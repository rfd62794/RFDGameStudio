# ADR-001: Unified Agent/Action Architecture — The Line

*Status: Proposed. Do not implement against this until reviewed and locked.*

## Context

Worker and Manager currently run on parallel, non-unified systems: separate `TaskType`/`ManagerTaskType` unions, separate `scoreX` functions, separate `evaluateXTick` argmax loops, separate facial-expression functions with overlapping logic. This was reasonable when Manager was new and small; it's become real duplication now that both entities have comparable depth. Separately, real work-time (`STATION_CONFIGS[id].protocolWorkTime`) is a fixed constant — every worker is functionally identical at execution, only behavioral state (stamina/morale/task) differs. And the arrival-time race diagnosed last turn exists partly *because* agents have no way to notice mid-commitment that they're not being productive and reconsider.

---

## Key Insight: Unifying Skill & Accountability Data

`worker.totalProtocols` and `worker.totalCornerCuts` are already tracked, persistent counters in the codebase.
- **Accountability** reads them as a ratio: *"Did this worker behave well?"* (`totalProtocols / (totalProtocols + totalCornerCuts)`).
- **Skill** can read the *same* counters as a magnitude: *"How much has this worker practiced this?"* (genuine earned competency derived from real historical repetitions rather than invented values).

---

## Decision Points

### 1. Unification Shape — Shared Interface, Not Merged Entity
Worker and Manager should **not** become one entity type. They have real, distinct domains (Worker: stations/orders/quality; Manager: supervision/coverage).
What will unify is the **shape** every action conforms to:
- A shared `Action<TAgent>` interface:
  - `id`: Action identifier
  - `scoreFn(agent: TAgent, world: KitchenState) => number`
  - `executeFn(agent: TAgent, world: KitchenState, dt: number) => void`
- Both `evaluateWorkerTick` and `evaluateManagerTick` reduce over these generically using a single shared argmax reducer, replacing two separate hand-written loops without erasing domain-specific differences.

### 2. Skill Representation — Per-Station Extension
`PRIMARY_STATION_OWNERSHIP_BONUS` already exists as a binary version of station competency (1.35× multiplier, on/off).
Skill levels represent the natural, graded generalization of this precedent:
- `skillLevel: Record<StationId, number>` per Worker.
- Scales real station `workTime` and/or Quality contributions gracefully.

### 3. Skill Growth — Earned via Practice Counters
Reusing `totalProtocols` per station (extending tracking granularity to per-station counts) as the real growth signal:
- Practice at a station increases skill with a real diminishing returns curve.
- **Tension & Open Question**: Earned competency via practice vs. Hire-time skill profiles. Default recommendation is earned competency as the core engine, with initial hire-time skill offsets integrated once the Hire/Fire system is implemented.

### 4. Self-Prioritization — Narrow Escape Hatch
To avoid regressing the task-commitment system (built explicitly to eliminate AI thrashing):
- If an agent is physically at its target (`dist < 45`), AND the station buffer is empty, AND that condition holds for a small duration threshold, THEN the commitment gate releases early.
- Prevents agents from idling at stalled stations without opening up arbitrary re-evaluation thrashing.

---

## Real Costs & Calibrations

- **Calibrated Margins**: Rest curve margins, Emergency Call bonus, risk-weighted targeting table, Quality 5-tier spread, and Break-encouragement numbers were calibrated against fixed work times. Variable skill work-times require re-verification against the new ranges.
- **Scope**: Touches `utilityScoring.ts`, `steering.ts`, `taskExecution.ts`, `types.ts`, and `KitchenCanvas.tsx`.
- **Facial Expressions**: Reconciles parallel hand-written expression functions into unified visual evaluation logic.
