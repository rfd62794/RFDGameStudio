# ADR-002: Station as a Reusable Base Object — Native Stock In/Out, Typed Stock State

*Status: Proposed. Do not implement against this until reviewed and sequenced.*

## Context

Two messages ago, physical Stock flow was proposed to fix a real problem: automated same-tick restocking made the global Stock Units pool functionally invisible, undermining the felt economic pressure it was built to create. This message sharpens that into something bigger and genuinely better — not a visibility patch, but a real architectural question: should `Station` become a formal base object with a native In/Out contract and a typed Stock-state model, the same class of unification ADR-001 already proved out for Worker/Manager?

**Real, confirmed current state, not assumed:** stations do not share a formal contract today. Grill/Assembly/Fryer share a *generic* pattern (process `orders[0]`, degrade or not via `isCornerCut`) but each has hand-written, special-cased transfer logic (`stationExecution.ts`: Queue routes to Grill and conditionally Fryer; Grill routes to Assembly; Assembly sets `burgerComplete` and routes to Window; Fryer just sets `friesComplete` on the same shared Order). Window is uniquely special-cased — it's the only station that both checks a completion condition (`burgerComplete && friesComplete`) *and* hands off to an external actor (the Customer). There's no real Stock-state typing anywhere; `burgerComplete`/`friesComplete` are ad-hoc booleans on `Order`, not instances of a general state model.

## Decision Points

**1. A real Stock-state model, three values:**
```typescript
type StockState = 'raw' | 'processed' | 'combined';
```
Raw = an unprocessed ingredient. Processed = a station's real output after a cook/prep action. Combined = the final Meal, assembled from multiple Processed stocks.

**2. A native Station In/Out contract:**
```typescript
interface StationIO {
  stockIn: StockState;
  stockOut: StockState;
  stockType?: string; // real, typed identity of *what* — 'patty', 'fries', 'meal' — not just its state
}
```

**3. Real station role mapping, grounded in the actual current pipeline, not invented from nothing:**
- **Truck/Unload Station** *(new, physical, replacing the current HUD-button restock)* — produces Raw stock from Cash. This is literally "unloading the truck" as a real map location and worker/player action, exactly as originally pictured, rather than an abstract number tied to nothing.
- **Grill** — consumes Raw (patty), produces Processed (cooked patty). Same real station, same position, now with a formal contract instead of implicit array-shifting.
- **Fryer** — consumes Raw (potato), produces Processed (cooked fries). Only active once unlocked — this maps directly and cleanly onto the unlock infrastructure that just shipped.
- **Assembly** — unchanged in real position and role: finishes burger-specific processing. Under the new model, its real output becomes a typed Processed-patty rather than a bare boolean flag.
- **Meal Prep Station** *(new)* — consumes Processed (patty) + Processed (fries, if wanted) → produces Combined (Meal). This is the real, new, explicit, worker-performed combination action that currently happens invisibly inside Window's `if` check. It sits physically between Assembly/Fryer and Window.
- **Window** — simplifies. No longer checks combination at all; purely hands off an already-Combined Meal to the Customer. A real reduction in Window's responsibility, not just an addition elsewhere.

## Real Costs, Stated Plainly — this is not a small refactor

- Every station's transfer logic in `stationExecution.ts` gets rewritten against the new contract — not additive, a genuine replacement of code that has been stable and tested since early in this project.
- The `Order` model's `burgerComplete`/`friesComplete` booleans get replaced by real Stock-state objects — this touches Quality's degradation logic, the Fryer dual-pipeline's "same object reference" invariant (the single highest-risk assumption already identified once this session), and every existing test anchor that references those two fields directly.
- A genuinely new station (Meal Prep) means new coordinates, new rendering, a new real worker task, on top of the Truck/Unload station also being new. This is comparable in real size to the original Fryer dual-pipeline build, not a quick addition.
- This is real, valuable infrastructure for Coffee and Soda too — both would slot into the same In/Out contract cleanly rather than needing their own hand-written special cases, the same argument that justified ADR-001.
