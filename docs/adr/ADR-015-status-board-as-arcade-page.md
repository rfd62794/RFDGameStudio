# ADR-015: Status Board as an Arcade Page

**Status:** Accepted
**Date:** August 15, 2026
**Supersedes:** None
**Related:** ADR-008 (shared UI components — this page is built from them
exclusively), ADR-014 (shared engine modules as default — the Status
Board's `lastUpdated` discipline is the same "make it visible, don't make
someone remember to ask" principle, applied to documentation staleness
rather than code reuse)

---

## Context

The studio status rollup — a hand-written markdown file at
`docs/state/StatusBoard.md` — had no connection to the deployed arcade.
To see it, you had to know the file existed and open it in the repo. To
update it, you had to hand-edit markdown tables. To notice it was stale,
you had to remember to check. None of these are things that actually
happen reliably in a multi-thread studio with games in five different
categories and infrastructure in three different tech stacks.

The same session that produced this ADR found a concrete instance of the
cost: the hand-written Status Board contained a claim that `artGen` was
"built, not yet consumed" by Shoal and SlimeWorld — a claim that was
already factually wrong when it was written, because both games had been
actively consuming the module for weeks (verified by direct file read,
see ADR-014 §"Proof case"). The staleness was invisible because the file
had no mechanism for showing its own age. A reader had no way to know
when any given line was last checked, and no reason to suspect it might
be wrong.

Robert's direct framing: the status board "becomes part of the Arcade
itself, as a Dedicated Section/Page System." Not a separate internal
tool, not a third-party dashboard — a page in the same arcade that
already hosts the games, built from the same shared UI components the
games use.

---

## Decision

The status rollup moves from a hand-written markdown file to a
structured data source with two generated consumers:

1. **`ts/src/status/board.data.ts`** — the single source of truth. A
   typed array of `ProjectEntry` objects with explicit fields: `id`,
   `name`, `category`, `status`, `currentState`, `nextAction`,
   `supersededBy`, `link`, and critically **`lastUpdated`** (ISO date).
2. **Two consumers, one source:**
   - **Markdown** (`docs/state/StatusBoard.md`) — generated by
     `ts/tools/generate-status-board.ts` via the pure
     `generateMarkdown()` function. For repo/agent context. Carries a
     generated-file header so no one edits it by hand.
   - **Arcade page** (`ts/src/pages/StatusBoardPage.tsx`, routed via
     `?page=status`) — rendered from the same `board.data.ts`. For
     actually looking at it. Built entirely from ADR-008's existing
     shared components (`TabBar` for category switching, `Card` +
     `Badge` per entry). No new base components.

### Why the arcade, not a separate tool

The arcade is where the games live. The status board is about the
games. Putting it in the same place means a person browsing the arcade
— the most likely person to need the status information — is one click
away from it, not a repo navigation away. The "Studio Status →" link in
`GameSelector.tsx` makes it discoverable, not a URL param nobody knows
exists.

### `lastUpdated` as the staleness mechanism

The `lastUpdated` field is the whole point of moving this into the
arcade. Each entry carries its own date. The page renders it visibly per
entry. Staleness becomes something you can *see* — a date that's months
old jumps out immediately — rather than something you have to remember
to audit. This is the direct response to the documentation staleness
problem found earlier this session: the `artGen` claim was wrong for
weeks and nobody noticed because the file gave no signal of its own age.

### Routing

`?page=status` — same minimal `URLSearchParams` style as the existing
`?game=` routing. `page` and `game` are separate query param namespaces,
checked in that order in `Root`. Existing `?game=` links across the site
(itch.io descriptions, devlogs, etc.) are unaffected — the `page` check
short-circuits only when `page` is present, and falls through to the
existing game/selector logic otherwise. No new routing library.

---

## Consequences

**Positive:**
- One source of truth (`board.data.ts`), two renderings (markdown +
  arcade page). Editing the data file and running the generator updates
  both. No more hand-editing markdown tables.
- Staleness is visible in the UI itself — `lastUpdated` per entry, not
  buried in prose. A reader doesn't need to remember to ask "is this
  still current"; the date tells them.
- The page is built from ADR-008's existing shared components only —
  no new base components, no bespoke CSS beyond what a game-specific
  page would already be allowed. Consistent with the studio's shared-
  component discipline.
- Discoverable via a visible link in the arcade selector, not a hidden
  URL param.

**Negative / real constraint:**
- `board.data.ts` is still hand-maintained — the data doesn't update
  itself. The `lastUpdated` field makes staleness *visible* but doesn't
  eliminate it. A discipline of updating the data file at checkpoints
  (the same "refresh at natural checkpoints" rule the hand-written file
  already had) still applies.
- The markdown file is now generated, not hand-edited — anyone who
  doesn't know this and edits it directly will have their changes
  overwritten on the next generation. The generated-file header
  mitigates this but doesn't prevent it entirely.
