# Studio extension: every demo is a child project the swarm can address

**Read first (inside this worktree):** `AGENTS.md`, `AGENT_CONTRACT.md`,
`ts/src/games/arcade-manifest.json`, `ts/src/games/game-metadata.json`, and any existing
`studio/` modules for the house style.

## 1. Why this exists

Robert (2026-09-22): "Per-Demo wherever possible, the game studio needs an extension module to enable
this and better interaction on a per-demo level via the swarm, each demo is a sub-repo or child to the
studio."

The swarm keys everything by repo, so 41 game folders share one direction, one roadmap and one test
command. This module is the studio's side of the fix: it publishes what its demos are, where each
one's files live, and how to verify one demo without running the whole suite. AgentFlow's side (the
`Repo/child-id` address, per-child direction and caps) is specified in AgentFlow's
`docs/superpowers/specs/2026-09-22-child-projects-design.md` and lands separately. Nothing in this
directive depends on that.

Record the test counts before you start: `cd ts && npx vitest run`, and the Python suite
`uv run pytest -q -m "not slow and not e2e"`.

## 2. Scope

1. `studio/demos.py` (new; follow the layout and style of the existing `studio/` modules):
   - `@dataclass Demo`: `id`, `label`, `path` (repo-relative, the demo's primary folder), `stage`
     (from the manifest: `dev`, `published`, or whatever the data says), `published: bool`,
     `docs_path` (the `games/<id>/` folder when it exists, else `None`).
   - `list_demos() -> tuple[Demo, ...]`, built **only** from evidence already in the repo:
     `ts/src/games/arcade-manifest.json` (the generated arcade list), `ts/src/games/game-metadata.json`
     (tracking data), and the presence of `ts/src/games/<id>/` and `games/<id>/`. Sorted by id.
     A demo in the manifest with no folder, or a folder in neither index, is reported by
     `problems()` rather than dropped silently.
   - `demo_paths(demo_id) -> tuple[str, ...]`: the code, data, docs and test paths that belong to
     that demo. This is what a directive will declare as its working area, so it must not include
     shared engine paths.
   - `demo_check(demo_id) -> str`: the single command that verifies that one demo (a vitest filter
     over that demo's tests today). Return the command as a string; do not run it.
   - `write_children_index(path=Path("docs/children.json"))`: writes
     `{"version": 1, "children": [{"id", "path", "label"}...]}` - sorted, two-space indented, one
     trailing newline, so regenerating it produces no diff when nothing changed.
   - `problems() -> list[str]`: manifest/folder mismatches, a demo with no test file, a demo missing
     from `game-metadata.json`. Findings, not exceptions.
2. `docs/children.json`: generated by the module and committed.
3. A CLI entry the way this repo already exposes studio tooling (mirror an existing module's
   `python -m` or `studio` entry point - follow what is there, do not invent a new pattern):
   `demos list`, `demos paths <id>`, `demos check <id>`, `demos index` (writes the file),
   `demos problems`.
4. Tests beside the repo's existing studio tests: a temp-repo fixture with two fake demos, one
   manifest-only and one folder-only, covering `list_demos`, `demo_paths` (no shared engine paths),
   `demo_check`, `problems`, and that `write_children_index` is byte-stable on a second call.
5. A test asserting `docs/children.json` matches `write_children_index()` for the real repo, so a demo
   added to the arcade shows up to the swarm without anyone remembering to register it.

## 3. What NOT to do

- Do not change any game's code, data, balance or art. This directive adds a module, its tests, one
  generated index and a CLI entry.
- Do not run builds, servers or the deploy scripts. Do not run `demo_check`'s command.
- Do not edit `arcade-manifest.json` or `game-metadata.json`; they are inputs.
- Do not add a dependency. Standard library and what the repo already imports.
- Run one command per call: no pipes, no redirects (`2>$null`, `>file`), no `&&` or `;` chains, no
  `$(...)`, no heredocs. Each of those is refused and two refusals end the run.
- **Create no scratch or debug files.** If you need one, put it under `.devin-scratch/` and leave it
  there; deleting files is not permitted and a refused delete stops the run.
- Do not read, search, or glob outside this worktree.

## 4. Verification

Tests first; watch them fail. Then:
- `uv run pytest -q -m "not slow and not e2e"` - 0 failures, and no fewer tests than the count you
  recorded.
- `cd ts && npx vitest run` - unchanged from your recorded count. If the pre-existing MBB point-cap
  failure or the 13 pre-existing skips appear, say so in the report and do not try to fix them here.
- State in the report how many demos `list_demos()` found and what `problems()` says about the real
  repo. That list is the point of the module.

## 5. Rules for this run

- The run is NON-INTERACTIVE. Any tool call that needs confirmation is rejected and the run ends.
  Never install, download or fetch. Never try to set or clear environment variables.
- Commit to this directive branch only. Never push, merge, switch branches, or touch `main`.
- These are the only commands available to you: `uv run pytest`, `npx vitest run`, `git status`,
  `git diff`, `git log`, `git add`, `git commit`, `ls`, `cat`, `head`, `tail`, `wc`, `grep`.
- If a tool call is genuinely blocked, stop and write why in the Status row.
